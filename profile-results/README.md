# Profile 结果

这里保存每次性能分析采集的原始产物、执行材料和观察记录。

## 组织形式

采集按源码分支和完整 commit 分组，每次运行占一个独立目录。下面是目录示例。

```text
profile-results/
├── README.md
└── fix~example-f4cef25c0f6809483224913300d82358abc701d7/
    └── 20261117T120000Z-nsys/
        ├── execution/       # 采集命令、配置、代码版本、环境和日志
        ├── traces/          # 原始 trace 或归档定位记录
        ├── exports/         # 按需导出的统计表、截图等
        └── analysis.md      # 本次采集的观察与分析
```

- 第一层使用 `<分支名-完整SHA>`，分支在路径中的 `/` 写成 `~`，例如 `fix/example` 对应 `fix~example`。完整 SHA 使用实际受测的 40 位 Git commit。同一分支的不同 commit 分别归档。
- 第二层使用 `<UTC开始时间>-<工具>`，例如 `20261117T120000Z-nsys`。工具名使用小写字母、数字和连字符。重跑使用新目录，名称冲突时追加 `-02` 等后缀。
- Profile 以源码身份登记，策略可引用同一次采集。若运行时检出为 detached HEAD，记录选定的原始具名源码分支、实际 commit 和 detached 状态。

目录按实际使用创建；没有导出材料时不必创建 `exports/`。

## 文件职责

- `execution/`：记录实际采集命令及工作目录、工具版本和配置、被测源码路径、原始分支名、完整 commit 和检出状态，以及环境、负载、采集范围和日志。检出状态包含未提交修改情况。具体文件格式随采集工具确定。
- `traces/`：保留 profiler 生成的原始文件及其文件名，以便使用对应工具重新打开。
- `exports/`：按需保存统计表、截图等，并能够追溯到原始 trace 的事件或时间区间。
- `analysis.md`：记录采集目的、输入负载、关键事件或时间区间、观察到的瓶颈及待验证的假设。链接原始证据及相关 benchmark（如有）。区分观察事实与推断。

Git 忽略的原始 trace 通过随仓库保存的归档说明、`artifacts.yaml` 或 `manifest.json` 引用。归档记录应能定位原始文件，以便用对应工具重开。

策略的完整实现计划和最终决定写在 `strategies/`；本目录聚焦本次采集的证据。正式性能比较使用 `benchmark-results/` 中的独立评测结果，并注明相关采集与评测是否采用相同条件。
