# 工作项约定

工作项是工作区内组织代码、实验和结论的基本单位。每项工作对应一个工作项，记录在 `work/<ID>-<name>/item.md`。

## 类型

| 类型 | 前缀 | `ws new` 参数 | 工作流 | 粒度 |
| --- | --- | --- | --- | --- |
| 模型适配 | `ADP` | `adapt` | [adapt.md](../workflows/adapt.md) | 一个模型，或一项能力（TP、量化、流式等） |
| 性能优化 | `OPT` | `opt` | [optimize.md](../workflows/optimize.md) | 一个可证伪的假设；`OPT-0000` 为初始基线 |
| 缺陷修复 | `FIX` | `fix` | [fix.md](../workflows/fix.md) | 一个正确性问题 |
| 调研 | `RES` | `res` | [research.md](../workflows/research.md) | 一个待回答的问题，只产出结论 |

一个工作项可以包含多个候选 commit 和多轮实验。独立的新假设、新模型或明显扩大的范围另开工作项，并在“依赖”字段注明关系。

## 状态与决定

状态表示进展，取值：

| 状态 | 含义 |
| --- | --- |
| `planned` | 已建项，尚未开始 |
| `analyzing` | 调研、设计、建立基线、profile、提出假设 |
| `implementing` | 编写代码 |
| `validating` | 正确性验证、评测与对比 |
| `deciding` | 证据齐备，形成决定与交付 |
| `done` | 已结项（决定已记录） |
| `blocked` | 受阻，交接区写明原因与所需输入 |
| `cancelled` | 取消，写明原因 |

各工作流阶段与状态的对应关系见对应工作流文件。`done`、`blocked`、`cancelled` 与阶段无关，阶段字段保留最后所处阶段。

决定单独记录，取值 `push`、`pr-open`、`merged`、`keep-local`、`discard`、`n/a`（调研类），并注明执行状态，例如 `keep-local（已执行）`、`push（待用户授权）`。

## item.md 结构

由 `ws new` 从 [templates/](../templates/) 中对应的 `item-<type>.md` 生成。适配、优化、修复三类为 11 节完整结构，调研类（`item-res.md`）省略代码方案与实验表，采用精简 9 节结构。完整结构如下：

1. **状态与交接**：键值表，字段固定为 ID、类型、状态、阶段、决定、依赖、起点 commit、实现分支、最后可信状态、下一步、阻塞/待用户决定、更新时间（UTC）。会话结束前必须更新，续接时只读这一节即可定位。
2. **目标与验收**：目标场景、指标、验收标准；引用 `PROJECT.md` 的口径，工作项级覆盖须附用户确认记录。
3. **范围**：做什么、明确不做什么。
4. **起点**：仓库与完整 commit、worktree、模型/数据/环境快照、基线证据。
5. **分析**：适配写架构差异和设计决策；优化写瓶颈证据和假设。区分事实与推断。
6. **方案**：改动范围、预期收益或风险、回退方式。
7. **实验与验证日志**：按轮次追加，只追加不改写。
8. **门禁记录**：`ws gate --write` 追加的检查结果与逐项回应。
9. **审查记录**：独立审查 Agent 的意见与处理结果。
10. **结论**：实际结果、适用范围、最终 commit、决定及执行状态。
11. **知识沉淀**：本项产生的、写入 `knowledge/` 的条目链接。

## 索引与看板

- `work/README.md` 维护全部工作项的索引表（含已结项），每项一行：ID、名称、类型、简述、状态、决定、关键结果。
- `PLAN.md` 只保留一张表，只列状态不是 `done`、`cancelled` 的工作项，列为 ID、类型、简述、阶段/状态、文档、起点 commit。不写标题、说明或任务清单。
- 两张表都位于 `ws:` 标记注释之间，由 `ws new` 追加，由 `ws lint` 校验与各 `item.md` 一致。状态变化时同时更新三处。
- “简述”用一两句话说明对象和核心方法；目标与实测收益写在 item.md。
